# 수입불량방 → 영업수입불량차감 / 영업입력 설계

작성일: 2026-09-14. 이 문서는 설계이며 불량 차감 자동 입력을 활성화하지 않는다.

## 목적과 적용 범위

수입불량방의 지정 작성자가 남긴 차수·거래처·품목·수량을 추출하고 실제 ERP 정보와 매칭한다. 담당자가 매칭 결과와 입력 내용을 승인한 항목만 `영업수입불량차감`의 `영업입력`으로 등록한다. 단순 불량 보고의 발견과 ERP 차감 승인을 구분한다. 추가취소 현장 전달 흐름이 항상 먼저다.

대상 작성자:

| 업무 담당자 | 내보내기 파일에서 인정할 이름 |
|---|---|
| 박성수 | 박성수 |
| 정재훈 | 정재훈 |
| 조현욱 | 조현욱 |
| 김원영 | 김원영, 김원영차장 |

부분 이름 일치로 다른 사람을 포함하지 않는다. 작성자 이름, 승인자 카톡 이름, ERP 입력 담당자 계정은 별도 설정이다. 이름 변경은 명시적 별칭 매핑으로 관리한다.

승인자 정책은 사용자 답변 대기 중이다. 기본 설계안은 원문 작성자가 승인하며 강현우는 운영 화면으로 전체 진행 상태를 확인한다. 강현우 일괄 승인으로 선택하면 승인 대상만 변경한다. 내부 오류·주기적 보고를 담당자 카톡으로 추가 전송하지 않는다.

## 첨부 자료 확인 결과

`불량.txt`는 수입불량방 대화이며 저장 시각은 2026-09-14 17:04:34다. 기존 내보내기 파서로 5,042개 메시지가 읽혔다. 지정 작성자 메시지는 4,207개이며, 본문이 `사진` 또는 `파일:`로 시작하는 메시지를 제외한 텍스트는 1,679개다. 이 숫자는 등록할 불량 건수가 아니다. 사진 보충, 대화, 확인 요청, 삭제 메시지가 포함된다.

실제 김원영 표기는 `김원영차장`이다. 예시는 다음처럼 해석한다.

| 항목 | 추출값 |
|---|---|
| 차수 | 37-1 |
| 분류 | 카네이션 |
| 품목 원문 | SP믹스 |
| 수량 / 원문 단위 | 15 / 단 |
| 거래처 원문 | 미카엘 |
| 목적 화면 / 입력 구분 | 영업수입불량차감 / 영업입력 |

이 값들은 원문 추출값이며 실제 ERP 품목·거래처 매칭 성공을 뜻하지 않는다. `37-1`은 차수 문자열로 보존하고 연도·기간을 별도로 확인한다. `단`과 `박스`, `대`, `송이`를 임의 환산하지 않는다.

현재 `core.defect_analyzer.parse_defect_text()`로 이 예시를 실행하면 차수·분류·거래처는 추출되지만 `variety_details=[]`다. 첫 줄의 품목·수량을 헤더로만 취급하므로 그대로 실등록에 연결하면 안 된다.

원본 파일 전체는 분석·검증용으로만 사용한다. 과거 대화 전체를 승인 질문이나 차감 등록으로 재생하지 않는다. 실제 가동 시 별도의 수집 시작 기준선과 미처리 검토 목록을 둔다.

## 우선순위와 실행 순서

| 순위 | 작업 | 실행 방식 |
|---|---|---|
| 1 | 영업방 최신 추가취소 수집, 추가취소 승인 질문·답변·현장 전달·완료 알림 | 매 순회 최우선 |
| 2 | 불량 신규 수집, 매칭 질문·승인 답변, 승인된 영업입력·완료 알림 | 1순위 처리 기회를 준 뒤 짧은 작업 단위로 실행 |
| 3 | 수입방 주문 분석·검토 시트 | 별도 분석 프로세스, 화면 수집은 1·2순위 뒤 |
| 4 | 기타 방·일반 보고·원문 보관 | 30분 단위, 상위 작업 사이에 긴 일괄 실행 금지 |

최우선 승인 확인은 대기 답변을 기다리며 실행을 붙잡지 않는다. 읽어서 새로운 답변이 없으면 불량 처리에 기회를 준다. 반대로 추가취소 미응답이 하나라도 있다는 이유로 불량을 무기한 막지 않는다.

한 순회의 예:

1. 영업방 최신 확인 → 추가취소 대상 대조·신규 질문 준비.
2. 담당자 받은 대화에서 신규 답변을 읽고 추가취소 답변·전달·완료 알림 우선 처리.
3. 불량 쪽 준비된 작업을 한 단계 처리한다. 승인된 항목 저장/재조회가 있으면 신규 불량 질문보다 먼저 처리한다.
4. 즉시 1순위로 돌아간다.
5. 다음 기회에 불량방 새 메시지 수집 또는 다음 불량 질문을 처리한다.

불량 내부에서는 `입력 결과 재조회 → 승인된 입력 1항목 → 완료 알림 → 신규 원문 수집/승인 질문` 순으로 진행하되, 신규 수집이 밀리지 않도록 완료 작업 한 건마다 신규 수집 기회를 배정한다. 새 원문은 수집 즉시 로컬에 보존한다. 업무가 완료될 때까지 다음 신규 메시지를 무시하지 않는다.

카카오와 ERP 화면을 조작하는 실행기는 한 개만 둔다. AI 분석·마스터 읽기·서버 보관은 화면 실행기 밖에서 수행한다. 긴 내보내기, 사진 다운로드, 여러 ERP 행 입력을 하나의 선점 불가능한 함수로 묶지 않는다. 승인된 불량 10건이 있어도 10건을 연속 입력하지 않고 1항목 완료 후 추가취소로 돌아간다. 이미 누른 ERP 저장은 도중 취소하지 않으며 결과 확정 또는 결과 불명 보존 후 다음 작업으로 넘어간다.

같은 담당자 대화는 한 순회에서 한 번 읽은 결과를 추가취소·불량 승인 해석에 함께 제공한다. 전송 후 확인에는 반드시 새로운 대화 기록을 사용한다. 수정 전처럼 기능마다 같은 대화를 따로 저장하는 구조를 만들지 않는다. 이 공유는 기존 승인 함수의 인터페이스 변경이 필요하며 현재 구현됐다는 뜻이 아니다.

## 수집·추출·매칭

1. 방 이름과 작성자 허용 목록을 확인하고 원문 ID·작성 시각·수집 시각·본문을 저장한다.
2. 첫 줄 안의 품목·수량과 다음 줄 거래처를 모두 읽는다. 품목별 줄 구조, 여러 거래처, 여러 수량을 각각 항목으로 나눈다.
3. `불량` 단어가 없어도 수입불량방의 지정 작성자가 차수·거래처·품목·수량을 제시하면 후보로 수집한다. 바로 입력하지는 않는다.
4. 사진만 있는 글, 삭제 메시지, 단순 의견은 등록 항목을 만들지 않는다. `추가 불량 사진`은 보충 자료다. 사진 인식 결과로 수량을 확정하지 않는다.
5. 바로 앞 글의 거래처·차수를 임의로 물려받지 않는다. 다중 거래처나 농장/거래처 구분이 모호하면 후보와 원문을 보여주고 확인한다.
6. 실제 거래처 키, 실제 품목 키, 차수, 영업 담당자, 입력 가능한 단위와 실제 판매/출고 이력을 읽어서 대조한다. 동일 이름의 농장·원산지·규격 상품은 별도 후보로 유지한다.
7. 매칭 불명·필수값 누락·수량 초과 가능성은 확인 질문으로 보낸다. 미확정 상태에서는 승인받았다고 등록하지 않는다.

수입 주문용 `order_services.master()`의 조회·별칭 도구는 재사용 후보지만, 주문 등록 함수는 불량 차감에 사용하지 않는다. 기존 분류기의 불량 점수 98/95는 문장 분류 점수이며 이 업무의 실행 우선순위로 사용하지 않는다.

## 담당자에게 보낼 메시지

사용자 확정 흐름: **매칭 결과 제시 → 맞다고 답하면 해당 내용 입력 → 틀리다고 답하면 올바른 품목명 요청 → 품목명 답변 수신 → 실마스터 재매칭 → 수정된 전체 내용으로 재승인 요청 → 맞다는 답변 후 입력**. 품목명을 알려준 행위 자체는 입력 승인이 아니다. 매칭 수정과 승인 요청도 불량 업무에 속하므로 추가취소 처리보다 후순위다.

추가취소의 `가가 보내`와 섞이지 않도록 불량은 별도 표시 `불량1`, `불량2`를 사용한다. 표시는 저장 후 재사용하지 않으며 ERP 코드와 별개다. 승인자 개인방은 친구 목록에서 정확한 이름으로 연다.

실제 마스터를 확인한 뒤 보내는 승인 요청 템플릿:

```text
[불량 입력 승인 · 불량1]
작성자: 박성수 / 원문: 9월 14일 16:35
입력 위치: 영업수입불량차감 > 영업입력

차수: 37-1
거래처: 미카엘 → {확인된 ERP 거래처명·코드}
품목: 카네이션 SP믹스 → {확인된 ERP 품목명·규격·코드}
수량: 15단 → {ERP 입력 수량·단위}
판매/출고 대조: {실제 조회 결과}
기존 차감: {실제 조회 결과}

매칭이 맞으면 아래 내용으로 영업입력합니다.
불량1 맞아 / 불량1 틀려
입력하지 않으려면: 불량1 안함
수정 예: 불량1 수량 12단
```

중괄호는 개발 템플릿이다. 조회하지 않은 값을 채우거나 템플릿 그대로 실전송하지 않는다. ERP가 요구하는 금액·사유·대상 판매행 등이 있으면 승인 내용에도 포함한다.

명령 규칙:

- `불량1 맞아`, `불량1 맞습니다`, `불량1 승인`: 매칭 결과와 함께 제시된 최신 입력 내용의 승인으로 처리. 매칭 확인 뒤 같은 내용에 대한 입력 승인을 중복해서 묻지 않음.
- `불량1 틀려`, `불량1 틀립니다`: 입력을 보류하고 `불량1의 올바른 품목명을 알려주세요`라고 질문. 취소/안함과 구분함.
- 올바른 품목명 답변: `불량1 품목 {품목명}` 또는 해당 항목의 품목명 대기 문맥에 연결되는 품목명 원문을 수신. 여러 항목이 정정 대기 중이면 항목 표시로 구분하며 임의 연결하지 않음.
- 품목명을 받으면 실제 ERP 후보를 다시 조회하고 원문·기존 매칭·수정 매칭을 보존. 후보가 여러 개면 선택/보충 정보를 받아 확정하고 새 버전의 전체 매칭 결과를 제시해 재승인 요청. 품목 수정으로 단위/규격이 바뀌면 환산을 추정하지 않고 함께 확인함.
- 요청번호 없이 `맞아`/`틀려`라고 답한 경우에도 해당 담당자의 마지막 유일한 확인 질문에 명확하게 연결될 때 해석한다. 새 질문·여러 정정 대기로 대상이 모호하면 어떤 불량 항목인지 확인한다. 과거 버전에 대한 답변을 새 매칭의 승인으로 사용하지 않는다.
- `불량1 안함`: 입력하지 않음으로 종료하고 처리 알림.
- `불량1, 불량2 승인` / `불량1 승인 불량2 안함`: 묶음 또는 개별 처리.
- `불량1 보류`: 대기 유지, 일정 시간이 지나도 자동 승인/취소하지 않음.
- `불량1 수량 12단`, `불량1 거래처 ...`, `불량1 품목 ...`: 수정안 생성 → 다시 매칭 → 수정된 승인 요청. 기존 승인은 새 내용에 승계하지 않음.
- `보내`, `가가 보내`만으로 불량 ERP 입력을 승인하지 않음.
- 다른 사람이 보낸 승인, 원문/수정 요청보다 먼저 온 승인, 모호한 묶음/충돌 지시는 실행하지 않음.

입력 성공 시:

```text
[불량 처리 완료 · 불량1]
37-1 / 미카엘 / 카네이션 SP믹스 / 15단
영업수입불량차감 > 영업입력에 등록했습니다.
등록번호: {실제 저장 후 확인한 번호}
```

안함은 `입력하지 않도록 처리했습니다`로 알린다. 결과 불명을 성공으로 알리지 않는다. 승인 질문, 필수 매칭 확인, 처리 결과 외 기술 로그는 로컬 운영 화면에 둔다.

## 상태·중복·재시작

항목별 상태: `수집 → 분석 중 → 매칭 확인 필요 / 승인 질문 대기 → 승인 대기 → 승인됨 → 입력 대기 → 입력 중 → 저장 결과 확인 → 입력 완료 → 완료 알림 확인`.

`보류`, `안함`, `원문 수정으로 재승인 필요`, `이미 입력됨`, `입력 결과 불명`을 별도로 둔다. 입력 결과 불명은 새 입력을 만들지 않고 원래 결과 조회만 한다. 복구되면 같은 등록번호로 완료한다. 여러 항목 중 일부만 성공하면 성공 항목을 다시 입력하지 않는다.

매칭 정정 분기: `승인 대기 → 매칭 틀림 → 품목명 답변 대기 → 재매칭 중 → 재승인 대기 → 승인됨`. 틀리다는 답변을 받는 즉시 기존 버전의 입력 가능 상태를 해제한다. 정정 이후에는 이전 버전 승인 메시지를 다시 읽어도 실행하지 않는다. 재매칭 후 명시적 긍정 답변이 없으면 계속 대기한다.

각 항목은 원문 ID, 항목 ID, 업무 종류, 원문 작성자, 승인자, 원문/수정 버전, 매칭된 키와 단위, 승인 메시지 ID, 승인된 내용의 해시, ERP 저장 시도 ID, 등록번호, 완료 알림 ID를 연결한다. 한 행에서 답변 여부·저장 여부·알림 여부를 구분해 볼 수 있어야 한다.

중복 방지는 두 단계다. 동일 원문 ID 재수집은 동일 항목으로 처리한다. ERP에서는 거래처·품목·차수·수량·단위·판매행 등 실제 기록을 확인한다. 같은 본문을 다시 썼다는 이유만으로 무조건 중복 차감이라 판단하지 않는다. 동일 조건의 별도 불량이 있을 수 있으므로 후보를 보여주고 담당자가 구분하게 한다.

승인 후 저장 직전 원문/매칭 버전과 기존 차감 기록을 다시 확인한다. 매칭이 바뀌면 재승인이 필요하다. 저장 전에 시도 기록을 남기고, 저장 후 등록번호와 전체 필드를 재조회해 비교한다. 클릭 성공이나 화면 이동만으로 입력 완료 처리하지 않는다.

## 구현 단위와 실등록 전 확인점

예정 모듈:

- `defect_deduction`: 작성자 필터, 항목 추출, 버전·상태, 중복 검토.
- `defect_approval`: 불량 표시 배정, 담당자별 질문, 수정·승인·안함·보류 해석.
- `defect_services`: 실제 영업수입불량차감 조회/등록/결과 재조회 어댑터.
- 공통 받은 답변 처리기와 우선순위 실행기: 추가취소 우선, 불량 작업 단계 사이 복귀.
- 운영 화면: 원문/매칭/승인/ERP 등록번호/완료 알림을 항목별 표시.

현재 저장소에는 검증된 불량 차감 등록 어댑터가 없다. `order_services.register_bulk()`도 실제 ERP 등록 규격 미검증으로 차단돼 있다. 따라서 다음을 실제 화면 또는 공식 내부 API 자료로 확인해야 구현을 확정할 수 있다.

1. 정확한 메뉴·입력 구분과 필수 필드, 차감 수량의 부호, 단위, 금액·사유 입력 방식.
2. 원 판매/출고 행 연결 여부와 여러 행일 때의 선택 규칙.
3. 로그인 사용자/영업 담당자 표시 규칙과 권한.
4. 기존 차감 조회 방법, 고유 등록번호, 중복 방지 키, 저장 후 결과 조회 방법.

## 검증·도입 순서

1. 첨부 텍스트로 오프라인 추출 검토표를 만든다. 과거 항목을 등록하지 않는다.
2. 담당자·거래처·품목 매칭을 실마스터와 대조하고 모호한 케이스를 확인한다.
3. 사진 단독, 첫 줄 수량, 복수 품목/거래처, 단위 차이, 삭제·정정·중복을 회귀 테스트한다.
4. 맞아/승인/틀려/안함/묶음/수정/늦은 답변/다른 작성자 답변/재시작/부분 성공/결과 불명까지 모사한다. 특히 `틀려 → 품목명 → 재매칭`까지만 진행한 상태에서는 입력이 0건이어야 하고, 재승인 뒤에만 수정된 품목으로 정확히 1건 입력돼야 한다.
5. 추가취소 새 메시지·답변이 불량 처리 중 도착하는 시험으로 순서와 대기 시간을 측정한다. 처리 함수가 반환됐다는 이유로 성공 판정하지 않는다.
6. 검증된 어댑터를 연결한 뒤, 실제 담당자가 승인한 한 건으로 ERP 저장·재조회·완료 알림을 확인한다. 이후 범위를 확대한다.

이 설계에서는 현재 실행 중인 추가취소 매크로 설정을 변경하지 않는다. 불량 자동 입력은 구현·검증 후 별도로 활성화한다.
