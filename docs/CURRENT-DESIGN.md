# 현재 설계와 운영 경과 — 2026-11-13

## 처리 구조

main.py moyi-worker → agent_runtime의 단일 워커 → 수집/승인/영업방/추가취소 보관/수입방 발주/불량 답장·입력/일일보고를 순차 실행한다. 실행 중 다른 프로세스가 카톡 UI를 조작하면 안 된다. atomic_json으로 상태를 보존한다.

영업방·추가취소방의 원문 수집/웹 업로드 목표는 5분이다. 추가취소 보관 에이전트의 코드 주기는 300초다. workflow_config의 primary 기본값 5초는 스케줄러 확인 주기이며 실제 전체 수집·업로드 완료 주기와 다르다. 지연은 최근 stage_timing/에이전트 결과와 업로드 이력으로 확인한다.

## 업무 규칙

- 불량은 업체·품목·수량을 필수로 하며 농장 부재만으로 보류/재문의하지 않는다. 원문과 거래내역의 품종·색상·단위·포장 문맥을 함께 대조한다. 애매하면 비교 후보와 부족한 항목을 원문 뒤에 명확히 제시한다.
- 불량 완료 알림 수신자는 원문 작성자(source_author)다. 업체 담당자와 원문 작성자를 혼동하지 않는다. 결과불명 발송은 기록된 실제 수신방에서 대조한다.
- 과거 고정 40차 지시는 최신 정책이 아니다. 현재 로컬 설정은 source_next: 원문 43-1 → 불량 44차, 44-1 → 45차. 이미 저장한 건의 실제 차수는 보존한다. 영업지원 등록 이력에 따른 전환도 별도 모듈이 지원하므로 설정과 증거를 확인한다. ISO 주차/대시보드 주차로 자동 대체하지 않는다.
- 발주는 수입방의 명확한 발주 내용을 대상으로 한다. 기타 처리사항과 영업방 추가취소를 발주로 섞지 않는다. 원문에 표시된 차수, 업체키·품목키·수량·단위, 거래내역을 검증한다. 미승인/정보부족은 저장하지 않는다. 주문 보고는 승인된 주문 보고 수신자 범위를 따른다.
- 추가취소 누락 검증은 당일분, 평일 13시·16시 고정 슬롯을 지원한다. 강현우를 포함한 설정 수신자에게 중복 없이 알린다. 원문·전달내용·정정/취소 문맥을 대조하며 단순 문자열 불일치를 누락으로 확정하지 않는다.
- 일일보고는 daily_staff_reports 경로로 한국시간 17시, 등록 건 있는 대상에게 업체·품목·수량·실제 등록 차수를 순차 전송한다. 별도 스크립트로 중복 발송하지 않는다.

## 저장·중복·불확실성

order_api/order_input/order_registration 및 defect_services/defect_runtime가 검증과 저장을 담당한다. 승인·요청마커·원문 연결·등록일시·차수·담당자·영수증을 대조한다. 동일 업체/품목/수량이나 현재 전산 수량만으로 중복 또는 성공을 단정하지 않는다. 저장 전 결과불명 상태를 기록하고, 저장번호와 독립 재조회로 성공을 확인한다. 결과불명은 재전송하지 않는다. maintenance_hold는 자동 재문의·재등록을 막는다.

## 실제 사용 경과와 미해결 범위

10월에는 불필요한 농장 질문, 품목/업체 매칭, 차수 이력 조회 한도, 자동인증, 웹 원문 업로드, 추가취소 누락 검증, 구독 CLI 분석을 보완했다. 11월 초에는 불량 결과불명 대조와 기존 수기등록 연결, 신규 23요청/25품목 저장 및 두 차례 재조회 검증 기록이 있다. 이 수치는 당시 작업 결과이며 현재 전체 정상 여부를 뜻하지 않는다.

11월 5일 발주 조사에서는 현재 범위 대기 73/보류 38/기존등록대조 1, 자동등록 영수증 0이었다. 입력검증 가능한 9건의 전산 기존 수량은 조회됐으나 원문 반영 성공의 근거로 채택하지 않았다. order=ok는 폴링 성공이고 전산 저장 완료가 아니다. 최신 결론은 로컬 요청·영수증·로그로 다시 확인한다.

현재 업로드 작업은 코드 배포와 인수인계 정리만 수행했다. 실제 발주/불량 저장, 카톡 발송, 재시작은 수행하지 않았다. 전체 원본 유지보수 기록은 운영 PC docs/maintenance-log.md 및 data/maintenance_checkpoint.json에만 남겨 둔다.
